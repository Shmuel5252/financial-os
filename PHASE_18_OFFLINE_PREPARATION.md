## Evidence and immediate security finding

Repository/executed evidence: installed next-auth 5.0.0-beta.32 / @auth/core database-session action obtains `{session,user}` from the adapter, calls the configured callback with `{...session,user}`, then serializes its result as the HTTP response. MongoDB adapter converts `_id` to `id` and preserves other document fields. The former callback returned that entire object. Therefore the public response could include `sessionToken` (bearer credential), session `id`, `userId`, `expires`, complete adapter user (`id`, email/name/image/emailVerified and any additional persisted fields), and any additional session document fields. OAuth credentials are normally in a separate collection: this is not proof those were in real user documents or leaked in production.

An installed Auth.js HTTP-handler test with a synthetic adapter reproduced the exposure before the fix: 1 failed / 3 passed. It did not inspect real sessions, tokens or users. This is a proven code-path exposure, not a proven third-party compromise. Treat it as a release-blocking security finding until fixed deployment verification; do not infer historical exploitation or absence of it.

Smallest fix: reconstruct public session with only `expires` and `user.{id,name,email,image}`. ID is from server adapter user / JWT subject, never a request-supplied user ID; absent optional presentation values normalize to null. Never spread adapter/session objects. No change to cookies, PKCE, AUTH_SECRET, database strategy, expiry/update policy, sign-out or server-derived authorization. JSON expiry serialization remains ISO date. Synthetic HTTP tests cover the valid, expired, absent and anonymous paths, unchanged HttpOnly cookie handling and retained adapter inputs; a direct callback test covers JWT fallback/client update rejection and absent identity. Do not log payloads even while checking the fix.

Owner-reported deployed evidence: e7dbbcb is Ready on the staging primary domain; owner-authenticated `/api/ops/bindings` returned only `{"status":"forbidden"}`. This is denial evidence only, not green bindings, not proof of the allowlist configuration, and not an independently executed anonymous/second-user test. New fix is not deployed. Independent hosted binding verification, session response verification, actual staging principal and environment separation remain pending.

Bindings review: guard executes before any probe, exact immutable ID allowlist, no email authorization, disabled/malformed denies all. Authenticated non-operator and anonymous routes return bounded status only. Authorized response has fixed policy/enums; selector query/header inputs do not select configuration. Existing tests cover driver/auth failures and synthetic private values; added mixed valid-ID/wildcard malformed-list denial. No bindings production code or authorization model changed.
